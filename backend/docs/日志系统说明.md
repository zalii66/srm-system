# 日志系统说明

## 📍 当前日志保存位置

### 日志文件位置

日志文件保存在：`backend/logs/` 目录

### 日志文件类型

1. **`app.log`** - 应用日志
   - 包含所有级别的日志（DEBUG、INFO、WARNING、ERROR）
   - 最大文件大小：10MB
   - 备份数量：5个（会自动轮转）

2. **`error.log`** - 错误日志
   - 仅包含 ERROR 级别的日志
   - 最大文件大小：10MB
   - 备份数量：5个（会自动轮转）

### 日志格式

```
时间戳 - 模块名 - 日志级别 - 日志消息
例如：2025-11-07 12:57:13 - app.api.v1.endpoints.projects - ERROR - 获取项目失败
```

## 🔍 当前实现特点

### 优点

1. **文件轮转**：自动管理日志文件大小，防止日志文件过大
2. **分离错误日志**：错误日志单独记录，便于快速定位问题
3. **控制台输出**：开发时可以在控制台实时查看日志
4. **日志级别控制**：可以根据环境（开发/生产）调整日志级别
5. **性能友好**：文件日志不会影响数据库性能

### 缺点

1. **查询不便**：需要手动查看文件或使用 grep 等工具
2. **无法统计分析**：难以进行日志统计和分析
3. **无用户追踪**：无法快速查询某个用户的操作历史
4. **无操作审计**：缺乏业务操作审计追踪

## 🤔 是否需要写入数据库？

### 建议：**混合方案**

根据不同的日志类型，采用不同的存储方式：

### 1. 系统日志（保留文件日志）

**用途：**
- 应用运行日志
- 错误追踪
- 性能监控
- 调试信息

**存储方式：** 继续使用文件日志

**原因：**
- 日志量大，写入数据库会影响性能
- 主要用于开发和运维人员排查问题
- 文件日志查询效率高（grep、tail 等工具）

### 2. 操作日志（建议写入数据库）

**用途：**
- 用户操作记录（创建、修改、删除）
- 业务操作审计（审核、评审、审批）
- 数据变更追踪
- 安全审计

**存储方式：** 写入数据库

**原因：**
- 数据量相对较小
- 需要快速查询和统计
- 需要关联用户、资源等信息
- 便于前端展示和报表生成

## 💡 推荐方案

### 方案一：仅文件日志（当前方案）

**适用场景：**
- 中小型项目
- 日志主要用于错误追踪
- 不需要操作审计功能

**优点：**
- 实现简单
- 性能好
- 维护成本低

**缺点：**
- 无法查询用户操作历史
- 无法进行统计分析

### 方案二：文件日志 + 操作日志表（推荐）

**实现方式：**

1. **系统日志**：继续使用文件日志
2. **操作日志**：创建 `operation_logs` 表，记录关键业务操作

**操作日志表结构建议：**

```sql
CREATE TABLE operation_logs (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT COMMENT '操作用户ID',
    username VARCHAR(50) COMMENT '操作用户名',
    action VARCHAR(50) COMMENT '操作类型（create/update/delete/audit/evaluate）',
    resource_type VARCHAR(50) COMMENT '资源类型（project/quotation/supplier/user）',
    resource_id INT COMMENT '资源ID',
    resource_name VARCHAR(200) COMMENT '资源名称',
    description TEXT COMMENT '操作描述',
    ip_address VARCHAR(50) COMMENT 'IP地址',
    user_agent TEXT COMMENT '用户代理',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '操作时间',
    INDEX idx_user_id (user_id),
    INDEX idx_action (action),
    INDEX idx_resource_type (resource_type),
    INDEX idx_created_at (created_at)
);
```

**优点：**
- 兼顾性能和功能需求
- 可以查询用户操作历史
- 可以生成操作报表
- 便于审计追踪

**缺点：**
- 需要额外的数据库表
- 需要在前端展示操作日志

## 📊 日志分类建议

### 1. 系统日志（文件）

| 日志类型 | 示例 | 存储方式 |
|---------|------|---------|
| 应用启动/关闭 | 应用启动成功 | 文件 |
| 数据库连接 | 数据库连接失败 | 文件 |
| API 请求错误 | 500 错误 | 文件 |
| 文件操作错误 | 文件上传失败 | 文件 |
| 性能日志 | 查询耗时过长 | 文件 |

### 2. 操作日志（数据库）

| 操作类型 | 示例 | 存储方式 |
|---------|------|---------|
| 创建项目 | 用户创建项目"XX项目" | 数据库 |
| 审核供应商 | 管理员审核供应商"XX公司" | 数据库 |
| 评审报价 | 项目经理评审报价#123 | 数据库 |
| 修改用户 | 管理员修改用户信息 | 数据库 |
| 删除数据 | 删除项目"XX项目" | 数据库 |
| 登录/登出 | 用户登录/登出 | 数据库 |

## ✅ 建议

### 当前阶段（开发/测试）

**建议：** 继续使用文件日志即可

**原因：**
- 当前日志主要用于错误追踪和调试
- 文件日志足够满足需求
- 避免过早优化

### 生产环境

**建议：** 根据业务需求决定

**如果需要操作审计：**
- 添加操作日志表
- 记录关键业务操作
- 提供操作日志查询功能

**如果不需要操作审计：**
- 继续使用文件日志
- 定期清理旧日志
- 监控日志文件大小
